# System Architecture — KGJ Marketing Funnel Hub

**Status:** rancangan P0 disetujui; ekstensi per cabang dan galeri independen telah diimplementasikan di kode, migrasi lokal/live menunggu persetujuan · **Acuan:** brief bisnis v1.0 (14 September 2026) dan keputusan teknis proyek (15–24 September 2026) · **Diperbarui:** 24 September 2026

Brief PDF menetapkan tujuan dan prinsip sederhana, tetapi tidak memilih stack, keamanan, atau topologi environment. Pilihan di bawah adalah keputusan proyek sesudah brief, bukan klaim bahwa semuanya tertulis di PDF. Produk dan kriteria penerimaan ada di [PRD](prd.md); relasi dan constraint ada di [Database Design](database-design.md).

## Bentuk sistem

Satu **modular monolith** Next.js App Router (`src/app`) dengan TypeScript ketat, React, Tailwind CSS, dan shadcn/ui untuk CMS. Halaman publik menggunakan Server Components secara default dan JavaScript klien seperlunya. Admin mutations memakai Server Actions; batas HTTP eksplisit memakai Route Handlers. Jalur database/Auth/Storage/tracking berjalan di Node.js. Tidak ada backend terpisah, headless CMS, queue, Redis wajib, atau state manager global P0.

| Lapisan         | Pilihan P0                                                                             |
| --------------- | -------------------------------------------------------------------------------------- |
| Aplikasi/deploy | Next.js di Vercel; Node 24, pnpm 11.15.1, versi paket exact di `package.json`/lockfile |
| Data            | Supabase PostgreSQL; Drizzle untuk schema, migrasi, dan query domain                   |
| Identitas/media | Supabase Auth dan Storage                                                              |
| Validasi        | Zod di server untuk input tak tepercaya; UI boleh memberi validasi tambahan            |
| Sinyal          | Meta Pixel, Meta CAPI, dan tabel event internal                                        |
| Verifikasi      | Vitest, Testing Library, Playwright, database lokal; cakupan berdasarkan risiko        |

Alur: browser membuka `/{slug-cabang}` (atau memilih cabang di direktori `/`) → server membaca konten aktif melalui modul domain/Drizzle → halaman cabang menampilkan CTA `wa.me` final → ketika gate tracking aktif, interaksi membentuk canonical event → browser mengirim Pixel serta `POST /api/events` best-effort → server memvalidasi, menyimpan event idempotent, lalu mengirim Meta CAPI dengan timeout terbatas. GTM dan pengiriman event browser ke GA4 tidak digunakan. Tabel domain tidak diakses langsung oleh browser.

Jalur event internal aktif di lokal. Di production, `TRACKING_ENABLED` default `false`; pemilik mengubahnya ke `true` hanya setelah kebijakan privasi, konfigurasi Meta Pixel/CAPI, dan pemeriksaan rilis disetujui. ID Pixel, ID dataset CAPI, dan token CAPI wajib ketika tracking diaktifkan. Tidak ada pilihan consent pengunjung: saat gate aktif, skrip Pixel dimuat otomatis dan CAPI mengirim event baru yang berhasil disimpan. GTM tidak dikonfigurasi atau diparse oleh aplikasi.

## Batas modul dan antarmuka

- `src/modules/public-content`: konten publik aktif, satu kampanye eligible, produk dan CTA cabang; mutasi CMS menginvalidasi cache konten publik.
- `src/modules/admin`: autentikasi/otorisasi, validasi dan mutasi konten, media, audit, serta tampilan validasi event internal.
- `src/modules/tracking`: sesi/atribusi, canonical event, validasi, penyimpanan, dan pemetaan penyedia.
- `src/lib/db` dan `src/lib/supabase`: koneksi server, Supabase Auth/Storage, dan schema; kredensial tidak diimpor ke komponen browser.

### Ekstensi Link Bio per cabang (disetujui 22 September 2026)

`/` adalah direktori cabang aktif tanpa produk, CTA WhatsApp, atau event bisnis. Route Server Component `/[slug]` memuat hanya cabang aktif, assignment dan produk aktif, serta konten yang khusus dimiliki cabang itu; slug tidak ada/nonaktif memakai 404. `next.config.ts` mengalihkan `/b/{slug}` permanen ke `/{slug}` sambil mempertahankan query UTM. Seluruh Link Bio cabang memakai satu template/desain KGJ dan komponen publik yang sama. Renderer membentuk profil ringkas, konten unggulan, galeri independen milik cabang, lalu daftar CTA WhatsApp produk. Galeri memakai grid 4:5 dua kolom pada ponsel dan tiga kolom pada layar lebih lebar; enam item pertama terlihat dan kontrol **Lihat semua koleksi** membuka sisa item tanpa batas data. Setiap produk eligible tampil sekali pada daftar CTA sebagai anchor `wa.me` langsung. Saat tracking aktif, klik CTA mengirim `Contact` dengan konteks produk dan cabang halaman; Link Bio tidak mengirim `ViewContent` karena tidak memiliki katalog atau halaman detail produk. Interaksi galeri tidak mengirim event bisnis. Kegagalan tracking tidak menahan navigasi. Tidak ada aplikasi, provider, role, atau event baru. Carousel ulasan tidak diimplementasikan pada tahap ini.

Model baca cabang memakai fallback pengaturan bersama untuk identitas/headline/pengantar/logo dan nilai teks produk yang tidak di-override. Tindakan CMS **Gunakan gambar bawaan** tetap berlaku untuk logo cabang. Galeri hanya membaca `gallery_items` aktif milik cabang menurut `sort_order`; tidak ada fallback global dan tidak ada hubungan ke assignment produk. Kampanye dan tautan juga hanya dibaca ketika `branch_id = cabang`; baris lama `branch_id IS NULL` dipertahankan tetapi tidak menjadi konten publik. Section `gallery` dan `products` dapat diatur terpisah. Section cabang memakai konfigurasi bersama jika belum mempunyai satu set konfigurasi sendiri. Setiap mutasi tetap memakai Auth, Zod, audit log, serta invalidasi path halaman terkait. Slug cabang adalah URL publik yang stabil; perubahan setelah dibagikan harus diberi peringatan di CMS.

Penyesuaian 24 September 2026 menambahkan `content_sections.public_title` untuk heading publik yang boleh kosong dan section `profile_logo` yang mempunyai kontrol aktif/nonaktif tetapi selalu dirender sebelum susunan section lain. Hero campaign kini menampilkan copy `title`/`description` sendiri bila tersedia. Carousel galeri adalah komponen klien kecil yang hanya aktif pada viewport mobile dan tanpa reduced motion; ia tidak membuat event, provider, atau state global baru. CTA WhatsApp tetap berupa anchor server-rendered biasa dan tidak bergantung pada carousel.

Navigasi CMS memakai satu daftar halaman cabang (`/admin/link-bio`) dan editor per cabang. Daftar tersebut membuka pembuatan halaman/cabang baru, sedangkan editor cabang mengelola identitas cabang, slug, nomor WhatsApp, konten, galeri, serta assignment produk dalam satu konteks. Panel **Galeri Produk** mengunggah dan mengurutkan visual cabang tanpa CTA; panel **Tombol WhatsApp** memilih jenis produk yang sudah ada, membuat jenis baru, serta mengelola teks, label, urutan, status, dan pesan tanpa pengaturan gambar. Data dasar jenis produk tetap tersimpan di `products` agar dapat dipakai lintas cabang dan menjadi kategori tracking kanonis, tetapi tidak mempunyai menu utama tersendiri. Pengeditannya tersedia sebagai kontrol sekunder di panel Tombol WhatsApp; rute lama `/admin/products*` mengalihkan ke daftar Halaman Link Bio. Rute lama `/admin/branches` mengalihkan ke daftar Halaman Link Bio dan `/admin/branches/{id}` mengalihkan ke editor cabang terkait; tidak ada workflow Data Cabang terpisah. Identitas, section bawaan, FAQ bawaan, dan pesan WhatsApp bawaan ada di `/admin/settings`. Rute CMS lama untuk konten, kampanye, dan tautan global mengalihkan ke pengaturan bersama atau daftar halaman; baris data global lama tidak dihapus. Default produk, nomor WhatsApp resmi per cabang, dan default pesan tetap menjadi sumber data bersama sesuai fallback yang ditetapkan.

Nama antarmuka `/admin/settings` adalah **Standar & Template KGJ**, menggantikan label **Pengaturan Bersama** tanpa mengubah route atau schema. Ia memasok fallback untuk identitas, standar WhatsApp, template section, dan template FAQ. Data cabang yang sudah tersimpan tidak ditimpa ketika standar diperbarui; kampanye, galeri, tautan, dan ulasan Google tidak memakai fallback ini.

`sort_order` tetap menjadi detail penyimpanan internal dan tidak ditampilkan sebagai input angka pada form CMS. Server Action pembuatan item menghitung posisi terakhir dalam scope yang sesuai, sementara edit mempertahankan posisi saat ini. Tindakan pemindahan Naik/Turun memvalidasi scope, menukar posisi, menormalisasi urutan daftar, mencatat audit log, dan menginvalidasi halaman admin/publik terkait. Tidak ada dependency drag-and-drop atau endpoint baru.

Pratinjau internal `/admin/preview/link-bio/{branchId}` memerlukan `requireAdmin()`, membaca data tersimpan dengan renderer publik yang sama, dan dapat memuat cabang nonaktif. Pratinjau tidak merender tracking dan mencegah navigasi tautan keluar; route publik `/[slug]` tetap menolak cabang nonaktif. Iframe CMS satu origin memuat pratinjau ulang setelah penyimpanan. Tidak ada draft server, endpoint publik baru, atau event tracking baru.

Proxy sesi/UTM berjalan pada `/` dan path `/{slug-cabang}`; kunjungan ke `/` menyimpan UTM untuk perjalanan ke halaman cabang tetapi tidak mengirim event. `/api/events` hanya menerima path cabang langsung pada origin situs; query string dibuang sebelum penyimpanan. Server memastikan cabang aktif dan `Contact.branch.id` sama dengan cabang halaman serta assignment produk-cabangnya aktif. `PageView` tetap tanpa `branch`; path halaman adalah konteks lokasi, bukan perubahan semantik event. `event_id`, idempotensi, dan navigasi WhatsApp non-blocking tidak berubah. Event historis dengan path `/b/{slug}` tidak diubah.

Migrasi Drizzle hanya menambah kolom/index dan mengubah keunikan section global menjadi keunikan per scope; data lama tetap scope global. Deploy live berurutan: pemilik meninjau dan menjalankan migrasi live, lalu deploy kode yang membaca schema baru. Tidak ada migrasi otomatis saat build Vercel. Pemeriksaan fitur dilakukan setelah cakupannya disetujui pemilik; tidak perlu staging atau suite tes besar.

### FAQ halaman (disetujui 22 September 2026)

FAQ memakai tabel `faqs` dengan scope `branch_id` nullable, tanpa provider eksternal atau API publik baru. Bacaan publik memilih FAQ aktif pada scope halaman; halaman cabang memakai FAQ global hanya jika belum mempunyai satu pun baris FAQ sendiri. CMS menggunakan Server Actions yang memerlukan profil admin aktif, validasi Zod, audit log, dan `revalidatePath` untuk halaman terkait. Kustomisasi pertama cabang menyalin FAQ global menjadi baris milik cabang. Konten FAQ ditampilkan sebagai teks biasa dalam accordion HTML; tidak dieksekusi sebagai HTML. Tambahan section `faq` memungkinkan urutan/visibilitas mengikuti pengaturan halaman. Ulasan Google tetap terpisah dan belum diimplementasikan.

`GET /api/public/config` adalah bentuk DTO internal jika dibutuhkan, bukan request kedua yang wajib untuk render halaman. DTO mengembalikan `campaign: null` atau satu kampanye, produk aktif dengan cabang eligible, serta section/tautan aktif secara deterministik. `POST /api/events` adalah **satu-satunya mutasi tracking publik**; Meta CAPI tidak memiliki endpoint publik. CMS dapat memakai Server Actions. Respons error HTTP memakai `{ "ok": false, "error": { "code", "message", "fields"? } }`; 400 JSON rusak, 401 belum login, 403 tidak berhak, 404 tidak ada, 409 konflik, 422 validasi domain, 429 pembatasan laju, 500 kesalahan internal tersanitasi.

Event kanonis memuat `eventId`, `eventName`, `eventTime`, `anonymousSessionId`, `pageUrl`, konteks `product`/`branch`/`cta`, lima UTM dan `source`/`campaign` bila diketahui, serta `metadata` kecil. Browser mengirim ID produk/cabang; server mengambil slug/nama yang berwenang dari database dan memastikan assignment Contact aktif. `PageView` tidak memiliki produk/cabang/CTA; `Contact` wajib produk, cabang, dan `whatsapp`; `LinkClick` wajib tautan aktif pada cabang. Retry `eventId` identik mengembalikan sukses `duplicate: true`; payload yang berubah material mendapat 409 tanpa menimpa event. Batas body 32 KiB dan `metadata` 4 KiB; validasi UUID, waktu, origin URL, panjang field, dan konteks dilakukan server-side. Rate limiting edge diterapkan pada `/api/events`, tanpa menjadikannya satu-satunya perlindungan.

## Tracking, navigasi, dan privasi

### Ulasan Google manual melalui Firecrawl (disetujui 24 September 2026)

`src/modules/reviews` memakai `POST https://api.firecrawl.dev/v2/scrape` dengan JSON schema, `cache: no-store`, dan timeout 60 detik untuk satu URL Google Maps tervalidasi pada satu cabang. Tidak ada SDK baru, endpoint publik, cron, atau browser call ke Firecrawl. Hanya `technical_admin` dapat memicu import; `admin` dapat mengelola filter/pilihan/hide/urutan hasil, menyimpan perubahan tampilan secara batch, serta menghapus permanen review terpilih setelah konfirmasi browser. URL sumber dibatasi ke Google Maps atau Google Search dengan anchor review `#lrd=`, sedangkan avatar dibatasi ke CDN Google sebelum dirender. Extraction menyimpan teks/waktu asli dan terjemahan Indonesia yang terpisah; hash deduplikasi tetap memakai data sumber asli. Saat gagal, error tersanitasi disimpan pada source dan review lama dipertahankan. Renderer hanya membaca source aktif, review tidak hidden yang memiliki terjemahan Indonesia, memenuhi minimum rating, serta mode otomatis atau pilihan manual; kartu publik tetap memiliki link sumber dan tidak membuat event tracking.

Cookie first-party `kgj_sid` menyimpan UUID acak dengan expiry bergulir 30 menit; atribusi lima UTM disimpan di cookie bertanda tangan. Cookie memakai `SameSite=Lax`, `Path=/`, dan `Secure` saat production. Tidak ada fingerprinting atau identitas lintas perangkat. UTM pertama yang tidak kosong dipertahankan; direct tidak menghapusnya; set UTM eksplisit berbeda memulai journey baru.

Pada klik WhatsApp, kode klien membentuk satu event, mengirim Pixel bila dikonfigurasi, lalu mengirim request event `keepalive` tanpa `await`, `preventDefault`, interstitial, atau redirect buatan. Anchor `wa.me` tetap tujuan navigasi. Server menyimpan event lebih dulu, lalu mengirim CAPI dengan timeout dan retry terbatas memakai ID sama. Pengiriman P0 best-effort, bukan janji delivery sempurna. Kegagalan Pixel, CAPI, maupun insert event tidak boleh menggagalkan WhatsApp.

Default deployment aman: tracking production nonaktif sampai `TRACKING_ENABLED=true`. Berdasarkan keputusan pemilik 23 September 2026, pengunjung tidak diberi kontrol consent dan tracking otomatis berjalan saat gate tersebut aktif; kebijakan privasi publik harus menjelaskan pemrosesan ini sebelum live. `_fbp`, `_fbc`, IP, dan user-agent hanya diteruskan ke Meta sebagai data transport dan tidak boleh disimpan di tabel event atau log biasa. Log server memuat kategori error, waktu, provider, dan ID event seperlunya; tanpa cookie, token, payload lengkap, IP, atau user-agent.

### Analytics event internal (disetujui 25 September 2026)

`/admin/tracking` tetap route autentikasi yang sama, tetapi menjadi dashboard Analytics untuk seluruh role admin dengan tab Detail event sebagai pemeriksaan operasional. Modul server-only `src/modules/admin/tracking` memvalidasi parameter query memakai Zod lalu membaca event pada rentang waktu yang dibatasi. Agregasi hanya menggunakan event dan snapshot yang sudah tersimpan: total/timeline `PageView`/`Contact`/`LinkClick`, rasio klik WhatsApp, peringkat produk menurut `Contact`, `source`/`utm_source`, serta `campaign`/`utm_campaign`. Konteks cabang untuk `PageView` diturunkan saat baca dari `page_url` cabang yang telah diverifikasi oleh ingest; `Contact` sudah menyimpan cabang. Event `ViewContent` historis tidak dirender maupun diekspor, dan endpoint baru menolaknya. Data device, browser, IP, lokasi, leads, pembayaran, dan omzet tidak dikumpulkan maupun ditampilkan. Tidak ada endpoint publik, provider, tabel, atau mutasi baru.

### Ekstensi Analytics dan provider (disetujui 25 September 2026)

Keputusan ini menggantikan batas Analytics internal sebelumnya. Browser mengirim `LinkClick` secara best-effort untuk tautan aktif tipe `secondary`/`social`; server memverifikasi tautan tersebut milik cabang URL dan menyimpan snapshot label/jenis tautan. Browser mengirim Pixel custom event bila Pixel dikonfigurasi. GTM dan `dataLayer` tidak digunakan. Kegagalan tracking tetap tidak memblokir navigasi tautan atau WhatsApp.

Route authenticated `GET /api/admin/analytics/export` memvalidasi filter Zod yang sama dengan detail event, membatasi hasil ke 10.000 baris, menerbitkan CSV tanpa ID sesi atau data transport, dan memasukkan audit log tersanitasi. Dashboard membandingkan rentang dengan rentang sebelumnya yang panjangnya sama. Ingest mengklasifikasikan user-agent secara server-side menjadi device `mobile`/`tablet`/`desktop`/`other` dan browser `Chrome`/`Safari`/`Firefox`/`Edge`/`Other`, lalu membuang user-agent mentah. Dari header Vercel ia hanya menyimpan country code dan nama kota; tidak menyimpan IP, region, kode pos, koordinat, atau timezone. Kota dengan kurang dari lima event tidak dirender.

Panel provider bersifat on-demand dan independent dari event internal: Meta Insights memakai `META_AD_ACCOUNT_ID` dan `META_MARKETING_API_ACCESS_TOKEN` yang terpisah dari token CAPI; GA4 Data API memakai `GA4_PROPERTY_ID`, email service account, dan private key server-only. Keduanya memakai timeout dan `cache: no-store`, tidak menjadwalkan sinkronisasi, serta menampilkan status belum terhubung/gagal tanpa mengekspos secret. Kredensial harus dikelola di environment deployment, dan akun service GA4 diberi akses baca properti. Endpoint API Google memakai `properties/{property}:runReport`, sebagaimana [dokumentasi GA4 Data API](https://developers.google.com/analytics/devguides/reporting/data/v1); geografi memakai header deployment yang [didokumentasikan Vercel](https://vercel.com/docs/headers/request-headers).

Kartu `PageView` dan kolom **Buka** adalah volume pembukaan mentah; refresh menghasilkan event baru. Agar kategori teknis tidak mengembang akibat rangkaian event dari satu kunjungan, peringkat sumber, kampanye, perangkat, browser, negara, dan kota mengelompokkan `PageView` menurut `anonymous_session_id` lalu menghitung satu sesi per nilai. Sumber/kampanye yang kosong bukan atribusi yang ditebak dan ditampilkan sebagai `Tanpa UTM source`/`Tanpa UTM campaign`; negara dirender sebagai nama Indonesia dan kode ISO. Batas privasi kota tetap memakai jumlah event minimal lima, meskipun nilai yang ditampilkan adalah jumlah sesi.

### Attribution URL Meta Ads (disetujui 25 September 2026)

Jalur ingest tidak menerima ID Meta khusus atau `fbclid` untuk penyimpanan internal. Ia tetap memakai lima UTM yang telah disanitasi dan ditandatangani dalam journey: `utm_source=meta`, `utm_medium=paid_social`, `utm_campaign` (campaign), `utm_content` (ad set), dan `utm_term` (ad). Nilai berasal dari destination URL yang dikonfigurasi di Ads Manager dan diperlakukan sebagai attribution yang diberikan URL, bukan klaim ID Meta yang diverifikasi aplikasi. `source`/`campaign` dipetakan dari `utm_source`/`utm_campaign`; semua lima nilai disimpan pada setiap event hingga `Contact`, dan `utm_content`/`utm_term` ditampilkan pada Detail event serta ekspor CSV. Tidak ada event Lead/Purchase, callback WhatsApp, atau join ke transaksi.

Verifikasi production dilakukan oleh pemilik setelah environment aktif: pastikan `TRACKING_ENABLED=true`, Pixel ID, dataset ID, dan token CAPI tersedia di deployment; buka satu destination URL Meta ber-UTM; klik CTA WhatsApp; lalu periksa `Contact` browser dan server di Meta Test Events/Events Manager menggunakan `event_id` yang sama. Kode dapat menjamin nilai event ID yang dikirim, tetapi status deduplication dan penerimaan provider hanya dapat dibuktikan di akun Meta production. Checklist ini tidak menambah halaman perantara atau mengubah navigasi `wa.me` langsung.

## Akses, keamanan, dan operasi

Halaman publik tanpa login. CMS memerlukan sesi Supabase Auth yang divalidasi server **dan** baris `admin_profiles` aktif. `admin` mengelola konten/validasi event; `technical_admin` juga mengelola profil admin dan diagnostik. Semua mutasi divalidasi server-side dan mencatat diff audit tersanitasi. Request mutasi berbasis cookie harus same-origin. Akses tabel domain melewati modul server dan role database aplikasi berprivilege minimum. RLS pada tabel yang terekspos Supabase menolak akses langsung `anon`/`authenticated` secara default. Browser Supabase hanya untuk Auth dan Storage yang disetujui. Bucket aset dibaca publik, ditulis admin terotorisasi dengan validasi MIME, ekstensi, ukuran, dan path. Token CAPI, secret Supabase, serta password database hanya ada di server/environment.

Hanya dua environment: **local** (Next.js + Supabase Local/Docker) dan **live** (Vercel + proyek Supabase hosted tersendiri). Tidak ada staging Supabase atau gate Vercel Preview P0. Jangan memakai kredensial live untuk pengembangan/CI. Supabase CLI mengelola layanan lokal; migrasi Drizzle mengelola schema aplikasi. Setelah `supabase db reset --local`, jalankan `pnpm db:migrate:local` secara terpisah karena reset tidak menjalankan migrasi Drizzle. Pada laptop Windows yang diuji, port lokal dapat dipublikasikan di semua interface; pemilik menjaga firewall dan menghentikan stack saat tidak dipakai. Operasi Git, provisioning live, dan persetujuan migrasi tetap milik pemilik proyek.

Perubahan schema: ubah Drizzle → hasilkan/tinjau migrasi → terapkan dan verifikasi lokal → persetujuan eksplisit pemilik → migrasi live terpisah dari build Vercel → deploy kompatibel dan smoke check singkat. Migrasi live dijalankan manual oleh pemilik melalui `pnpm db:migrate:live` dengan `DATABASE_LIVE_MIGRATION_URL` sementara dari koneksi admin Supabase; nilai ini tidak masuk Vercel dan berbeda dari `DATABASE_URL` role aplikasi. Gunakan perubahan backward-compatible; rollback aplikasi hanya jika schema masih kompatibel. Retensi event 24 bulan dilaksanakan job terautentikasi berbatas batch sebelum launch; jangan mengaktifkannya sebelum verifikasi lokal. Akun `technical_admin` pertama dibuat lewat prosedur Auth + profil server-side, bukan seed atau sekadar email yang diketahui.

Operasi live yang masih menjadi tugas pemilik: atur [WAF Vercel](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) untuk `/api/events` memakai batas per IP dan global langsung pada konfigurasi Firewall Vercel; jadwalkan `GET /api/cron/events-retention` dengan header `Authorization: Bearer <CRON_SECRET>` setelah verifikasi lokal (maksimal 500 event kadaluarsa per eksekusi); buat pengguna di Supabase Auth sebelum `technical_admin` menghubungkan ID-nya melalui CMS. Tidak ada WAF, cron, atau pengiriman penyedia yang diaktifkan hanya dengan menambahkan kode ini.

Sebelum menjalankan tes, konfirmasi cakupan ke pemilik sesuai `AGENTS.md`. Saat fitur selesai, verifikasi secukupnya: aturan domain/tracking dengan Vitest, interaksi dengan Testing Library, constraint dan akses DB dengan Supabase Local, alur WhatsApp/browser dengan Playwright; adaptasi provider memakai fixture di CI dan validasi nyata dilakukan saat gate rilis. CI tidak menyentuh live. Bukti lulus hanya boleh diklaim untuk pemeriksaan yang benar-benar dijalankan.
